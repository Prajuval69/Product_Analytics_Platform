# Churn methodology

The task is future 30-day churn for customers aged at least 30 days, active in the previous 30 days, and not already cancelled. Churn means cancellation in the future horizon or no qualifying active event during the entire future horizon. SQL and daily reporting share the `churn_outcome` macro.

The observation cutoff is inclusive through its UTC day. Predictors observe dates C−29…C; labels observe C+1…C+30. SQL predicates bound activity, feature use, successful revenue and support openings by cutoff. Subscription tenure uses a known subscription start; no future cancellation timestamp is included as a predictor. Signup plan is immutable. Future activity contributes only to the label expression, which is kept outside the Python predictor allowlist. Source `churn_signal`, current lifecycle_status and customer_segment are never predictors.

The default snapshot dates are 2025-05-03 (training), 2025-07-02 (validation), 2025-08-31 (testing), and 2025-09-30 (unlabeled current scoring). The first three are history_end minus 150, 90 and 30 days. Sixty-day separation prevents overlap between one snapshot's observation/outcome span and the next. Users may recur across snapshots to mimic rescoring existing customers; identifiers are excluded. This measures temporal generalization, not unseen-user performance. Eligibility changes can create population shift.

Numeric predictors: signup tenure, trailing sessions/active days/active event count, activity recency, distinct used features, key-feature use count, successful trailing revenue, support openings and subscription tenure. Plan is one-hot encoded. The preprocessing pipeline imputes medians, standardizes numeric columns and ignores unknown categories; it is fitted on training rows only. SQL features are required complete before training; imputation supports future runtime robustness.

The baseline is Logistic Regression with balanced class weights and fixed seed. Validation F1 selects a classification threshold from 0.20 through 0.80 in 0.05 steps. The test set is never used to tune the threshold or refit the model. ROC-AUC uses probabilities; precision, recall, F1 and the `[TN,FP;FN,TP]` confusion matrix use the selected threshold. Evaluation also records class prevalence and a constant-majority accuracy/AUC reference. No optional Random Forest is needed to satisfy the specification.

The evaluated model is persisted and used for current scoring. Fixed risk bands are low <0.30, medium 0.30–<0.70, high ≥0.70; bands are not the tuned binary threshold. Already-cancelled or inactive customers remain in the health export but have null prediction fields, indicating ineligibility rather than zero risk. `feature_metadata.json` stores the feature list and horizon, `evaluation.json` stores actual held-out results, `coefficients.csv` stores transformed coefficients, and CSVs retain feature/test/scoring rows. Positive coefficients raise log odds holding others fixed; correlated engagement predictors make coefficient interpretation conditional.

Synthetic engagement and dropout are latent generator variables never stored as labels or predictors. They induce noisy correlations, not external evidence. Reported model metrics do not imply real-world value. No probability calibration, drift monitor, model registry, fairness audit or production deployment is claimed. A real deployment would validate labels, calibrate risk, monitor drift, compare baselines and evaluate intervention outcomes.
